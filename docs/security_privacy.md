# Security & privacy

This is a sandbox/reference implementation. The controls below are implemented in the shipped app;
production hardening items are called out explicitly.

## Trust boundaries

```text
Browser ──cookie/TLS──> Express app ──TLS──> PayPal sandbox
   │                       │
   │                       ├──TLS──> LLM provider
   │                       └──local──> JSON file store
   └──PayPal SDK iframe──> sandbox.paypal.com (hosted by PayPal)
```

The browser never receives PayPal client secrets, LLM keys, JWT signing secrets or the PII pepper.
Card data is entered only in PayPal-hosted surfaces; the app never sees PAN/CVV.

## Authentication & sessions

- Server-side session cookie `sid`: signed, `HttpOnly`, `SameSite=Lax`, `Secure` when
  `COOKIE_SECURE=true` (set in production/Render).
- Optional bearer access token is resolved server-side; refresh tokens are hashed at rest.
- Passwords use salted `scrypt` with timing-safe comparison. Argon2id is a production upgrade path.
- Guest sessions are explicit (`POST /session/guest`). Sign-in merges the guest cart and claims
  eligible guest orders.
- Logout clears auth/session cookies.

## CSRF, CORS and framing

- State-changing requests require the double-submit pair: `csrf` cookie + `x-sp-csrf` header.
- PayPal webhooks are exempt from browser CSRF because they are server-to-server and signature-verified.
- Origin checks allow same-origin, configured `WEB_ORIGIN`, Render's external URL and localhost dev.
- CSP restricts scripts/frames/connect sources to self and PayPal; `object-src 'none'`,
  `base-uri 'self'`, `nosniff`, `Referrer-Policy`, and `X-Frame-Options: SAMEORIGIN` unless explicit
  preview embed origins are configured.

## Authorisation

| Role | Access |
|---|---|
| Guest | Own session cart/orders, checkout |
| Customer | Own user cart/orders |
| Merchant | Own products/orders/lines, fulfilment, scoped refunds, analytics |
| Admin | Platform overview, reconciliation, merchant oversight |

Cross-tenant order/product reads return 404/403 rather than leaking existence. Merchants cannot mark
orders paid. Only the payment service writes `paid`, after capture verification.

## Input validation & injection defence

- Zod schemas validate route bodies/queries.
- The agent tool bridge validates model arguments against `contracts/agent_tools.json`; unknown fields
  are rejected.
- No request body is spread into store queries. The file store implements a bounded query matcher;
  there is no Mongo operator injection surface in the default build.
- The model has no generic HTTP/shell/eval tool and no payment tool.
- JSON body limit is 256 KB; chat and checkout paths are rate limited.

## Payment security

- PayPal Orders v2 is created/captured server-side with OAuth2 and `PayPal-Request-Id` idempotency.
- Capture verification checks order reference, amount, currency, capture status, uniqueness and split
  settlement before any paid transition.
- Webhook signatures are verified against PayPal using `PAYPAL_WEBHOOK_ID`; events are deduplicated by
  `event.id`. Missing headers or verification errors are recorded as unverified and answered 200, never
  applied as payment state.
- Invoice ids include the internal order id so ephemeral-store counter resets cannot collide with a
  previously captured PayPal invoice.
- Refunds are merchant-scoped and use PayPal's refund API; the agent cannot call them.

## Rate limiting & abuse

Fixed-window limits are keyed by session (falling back to IP) for auth, chat, checkout, payment and
global traffic. Buckets are swept to bound memory. LLM turns have iteration/time budgets. Simulator
`/dev/*` helpers are disabled in production sandbox mode.

## Data protection

- Analytics uses a strict event/prop allow-list and rejects PII keys.
- PII correlation uses HMAC with `PII_HASH_PEPPER`; raw payer email is not stored in analytics.
- Payment response snapshots are stripped before storage/API exposure.
- Structured logs redact passwords, tokens, authorization/cookie headers, secrets, email and card-like
  numbers.
- Local `.env`, `.data/`, logs and test artifacts are gitignored. `.env.example` contains placeholders only.

## Secrets

Required secrets are supplied by environment/Render, never committed:

- `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_WEBHOOK_ID`
- `LLM_API_KEY`
- `JWT_SECRET`, `PII_HASH_PEPPER` (generated by Render)

Rotate any credential that has been pasted into chat, logs or a public issue. Use sandbox credentials
for demos; never use live PayPal keys in this project.

## Threat model summary

| Threat | Control |
|---|---|
| Prompt injection spends money | No payment tool; human approval; server-side capture verification |
| Forged/replayed webhook | Signature verification + event dedupe + full-order re-verification |
| Double charge | Idempotency keys, per-order lock, duplicate invoice/capture guards |
| Price tampering | Server quote hash; model text never sets price |
| Cross-tenant read/refund | Ownership/role checks; 404 on cross-tenant reads |
| CSRF | Double-submit token + origin check |
| Secret leakage | Env-only secrets, log redaction, gitignore, no secrets in frontend |
| Stock oversell | TTL holds, availability recheck, transactional stock commit |

## Production hardening still required

- Replace the file store with a real database and shared locks before horizontal scaling.
- Use durable encrypted storage/backups and a managed secret store.
- Upgrade password hashing to Argon2id and add account lockout/MFA for real users.
- Add centralized audit logging, alerting, dependency scanning and penetration testing.
- Complete PayPal marketplace/partner onboarding before any live multi-seller payout.

## Incident response

1. Contain: disable checkout/live LLM flags, rotate affected secrets, revoke sessions/tokens.
2. Preserve: request ids, order timeline, payment attempts, webhook events and redacted logs.
3. Reconcile: use admin reconciliation against PayPal; never mark paid manually.
4. Remediate: add a regression test, update this document and the relevant runbook.
