ShopPilot turns a sentence — “noise-cancelling headphones for flights under $350” — into a priced, stock-checked order that may span several merchants, and stops there. The shopper approves. The agent has no payment tool, so it cannot spend even if it wanted to.

01A turn, end to end

Every turn is a bounded loop. The model chooses tools; the server executes them; the answer is checked before the shopper ever sees it.

The shopper says something in plain language

The message is parsed for category, budget and constraints, then added to a requirement the session carries forward — so “actually, cheaper” still knows the category.

The model is asked to use the catalogue, not its memory

A product request forces one search_products call before any answer (tool_choice: "required", reverted to auto immediately after, so it cannot loop). Everything it says about a product comes from a tool result.

Tool results are compacted before they reach the model

A five-product search returns 76% fewer tokens than the raw record — id, price, stock, rating and the six attributes that matter. The free Groq tier allows 8,000 tokens/minute, and a turn now costs about 2,600 instead of 10,000.

The answer is checked against what the tools actually returned

Every price in the draft is matched against this turn's tool payloads in both display and minor-unit form. A number that no tool produced is not shown — the answer is replaced with one built from the tool results. Amounts the shopper typed themselves are allowed through.

If the model is unavailable, the shop still works

A deterministic planner answers from the same catalogue and the same tools. The turn is labelled deterministic, never live — the UI says which path ran, and /api/v1/version reports it too.

02The tools

Fourteen, registered in one place and exercised by the test suite. Read the list for what is absent: there is no tool that can pay, capture, or move money.

03The money path

One cart can hold products from several merchants. PayPal pays a merchant, not a platform, so a multi-merchant basket has to be settled deliberately — and has to keep working when the account is not enabled for it.

01

Split settlement

One PayPal order, one purchase unit per merchant, each with its own payee. The commission is attached as a platform_fee.

02

Fees refused

If PayPal answers PLATFORM_FEES_NOT_SUPPORTED, the same order is rebuilt with payees and no fee. The shopper pays the same total; the platform earns nothing rather than failing the sale.

03

Split refused

If multi-seller payment is unavailable at all, the basket settles as a single payee. Every fallback is recorded on the order so the ledger shows which rung was used.

04

Merchant refunds & lifecycle

Merchants can issue full or partial refunds directly through PayPal's refund APIs (/v2/payments/captures/{id}/refund), updating seller settlement units and transitioning order state atomically.

Nothing is trusted from the browser. The amount captured is checked server-side against the order that was stored before the redirect. A capture whose amount or currency disagrees with the order is rejected, not reconciled after the fact.

04The rails

The interesting part of an agent that spends money is everything it is not allowed to do.

  • No payment toolThe agent can price a basket and prepare a checkout. Only a human click on the checkout page starts a PayPal payment.
  • No ungrounded pricesEvery figure in an answer is matched against the tool results for that turn. Failing means the text is replaced, not patched.
  • No stale pricesQuotes carry a hash of the priced basket. If a price or stock level changes between quote and order, the order is refused and the shopper re-reviews.
  • No double chargingOrder creation is idempotent on a client key; a replayed request returns the original order instead of creating a second one.
  • No silent failuresEvery turn reports which path produced it — live model, degraded, or deterministic — and /api/v1/version exposes the same fact.

05What is checked

97 tests across 8 suites (unit, integration, adversarial prompt-injection resistance, live agent evaluations, multi-seller settlement, and seed history), plus ten invariants the suite refuses to break: money conserves, stock never goes negative, settlement units always sum to the order total, merchant refunds transition state atomically, and the event log matches the orders it describes.
